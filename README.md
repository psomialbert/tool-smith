# smith (Toolsmith)

Agent-authored CLIs as **git repos**, adopted per project behind a **trust
gate** — a thin convention over [mise](https://mise.jdx.dev).
Works with any coding agent, not just one.

An agent that writes its own tools has nowhere trustworthy to keep them: a
script lives untracked on one machine (lost next session) or gets pasted back
into context every time, and pulling someone else's tool is a supply-chain
event an agent can be prompt-injected into. smith makes a tool a **git repo**
(source + manifest + self-test + a description of when to reach for it) that
you **adopt into a project the way you'd add any dependency — a reviewable
commit**. Nothing runs unvetted: until a tool is adopted, it only runs
sandboxed.

The loop: **author → (its own repo) → adopt (sandboxed self-test + vendored,
reviewed in a PR) → on PATH for the project.**

**Agent-agnostic by design.** A smith tool is just a CLI on your project's PATH
that speaks `--json`, so any agent can run one. `smith install` also *tells*
whatever agent you use that the tools exist, by refreshing a generated block in
your `AGENTS.md` or `CLAUDE.md` — no per-agent setup, no hand-written snippets
to keep in sync. Claude Code, Codex, Cursor, Gemini CLI: same tools, same trust
gate.

That block is the whole integration. Adopt a tool, run `smith install`, and your
existing `AGENTS.md` gains this — your own content above it untouched:

```markdown
# my project

My own notes.

<!-- smith:begin — generated by `smith install`; edits inside are overwritten -->
## Project tools (smith)

These are on PATH for this project. Run `smith lens` for the always-fresh index.

| tool | version | invoke | trigger |
|---|---|---|---|
| calc | v0.1.1 | `calc --json …` | Evaluate an arithmetic/logic expression safely and get a structured result. Use when a session needs to compute a number — precedence, %, //, **, sqrt/log/min/max/floor/ceil/trig, comparisons, and/or/not — without shelling out to python or risking `eval`. |
<!-- smith:end -->
```

Re-running `smith install` is a no-op when nothing changed, so it's safe in CI
against a tracked file. smith never *creates* `AGENTS.md`/`CLAUDE.md` — it only
updates one you already have.

## How trust works

Adopting a tool = `smith use` vendors its source under `.smith/tools/<name>/`
and pins it (repo + version + content hash) in `.smith/tools.yaml`. That's a
normal git diff your team reviews in a PR — **the PR review is the trust
gate**, exactly like reviewing any dependency.

- **Sandboxed until adopted.** `smith use` runs the tool's self-test in an OS
  sandbox (no network, writes confined to CWD+TMP, sanitized env) before
  vendoring, so unreviewed code is contained at adopt time.
- **Trusted per project.** A tool vendored + pinned in the reviewed
  `.smith/tools.yaml` is trusted *for that project* and goes on PATH (via
  mise) after `smith install`. Not global — scoped to the project that
  reviewed it, the way mise already scopes tool versions per project.
- **Discovery ≠ trust.** `smith search` finds repos by GitHub topic; found
  tools are only ever trusted through the adoption PR.
- **Integrity.** `smith install` re-hashes each vendored bundle against its
  pin and refuses on mismatch (go.sum-style). A teammate who clones the
  project and runs `smith install` gets the exact same tools. `smith verify
  --frozen` runs that check standalone as a CI gate (exit non-zero on drift).

See [SECURITY.md](SECURITY.md) for the full threat model — what smith defends,
what it doesn't, and how to report a vulnerability.

## Requirements

- [mise](https://mise.jdx.dev) — version/PATH management (smith wraps it)
- `git`
- A functional OS sandbox to self-test/try tools: macOS Seatbelt (built in)
  or Linux `bwrap` with unprivileged user+net namespaces. smith **fails
  closed** without one (see *Sandbox host requirements*).
- `gh` for `smith search` (optional)

## Install

`smith` is a single binary; it needs `mise` on PATH at runtime.

```sh
# one-liner (downloads the release binary for your platform)
curl -fsSL https://raw.githubusercontent.com/psomialbert/tool-smith/main/scripts/install.sh | sh

make install                       # from a clone: build + install to ~/.local/bin
```

The installer downloads over plain https (no auth); it falls back to `gh` if the
repo is private.

All paths also install the **cli-creator** authoring skill into
`~/.claude/skills/cli-creator/` (override with `SKILLS_DIR`/`SMITH_SKILLS_DIR`),
so authoring agents get the CLI contract without setup. Prebuilt binaries
(darwin/linux × arm64/amd64) are attached to each
[release](https://github.com/psomialbert/tool-smith/releases).

`smith install` separately keeps a project's adopted-tool index visible to
whatever agent is working there — see *Using smith with agents* below.

## Quickstart

```sh
# author a tool
smith new greet --runtime bash --desc "print a greeting"
cd greet && $EDITOR greet selftest.sh SKILL.md
smith publish --public         # git + create/push repo, tag v0.1.0, topic-tag smith-tool

# in a project, adopt it — a reviewable commit
smith use ../greet@v0.1.0          # sandboxed self-test, vendor, pin
smith review greet                 # read the source (TUI); comment lines -> agent report
git add .smith && git commit       # the adoption, for your team to review
smith install                      # realize it onto the project PATH
smith list                         # what's adopted in this project (+ install status)
greet alice                        # -> hello, alice

# ...or adopt an existing published tool
smith use github:psomialbert/smith-example-calc@v0.1.1   # a worked example
smith search json                                        # discover more by topic
```

## Using smith with agents

The safety model is the division of labor: an **agent authors and proposes**,
a **human reviews the PR and adopts**.

**`smith contract`** prints the authoring contract — required CLI behavior, the
self-test rules, and which limits are load-bearing versus merely unbuilt. Point
any agent at it (`smith contract --json` for machines). It exists because the
cli-creator skill installs out-of-band: an agent holding only the binary used to
have no way to learn the contract except being handed a path to this repo by
hand, where the most authoritative-looking file was a retired v1 spec.

Two things it says that are worth repeating here, because guessing wrong about
them leads to real architectural detours:

- **The sandbox binds the self-test, not the tool.** It applies at adopt time
  only. After `smith install`, a tool is a plain executable on PATH with your
  full privileges — it may download large files, start a daemon, use a local
  model. The only requirement is that `selftest.sh` proves something meaningful
  *offline*. (Caveat worth knowing: smith pins your vendored source, not what
  your tool fetches later.)
- **Heavy systems get a thin client.** If the real work is a daemon or a
  resident model, ship that as its own ordinary project and make the smith tool
  a thin `--json` client to it. The client is what gets adopted and reviewed.
  That's the sanctioned shape, not a workaround.

| Agents may | Humans own |
|---|---|
| `new` (author), `use`/`upgrade` (propose adoption), `diff`/`review`/`lens` (read), `search`, `list`, `doctor`, `install` | reviewing + **merging the adoption PR** (the trust decision) |

**Discovering a project's tools.** `smith lens` prints an agent-facing index of
the tools *this* project has adopted — each tool's trigger and how to invoke
it. It's project-scoped and always fresh (unlike the globally-exported
per-tool skills), so it's what an agent should run when it needs the current
truth.

`smith install` also keeps that same index visible without anyone having to
run `lens` first: it refreshes a smith-managed block (tool name, version,
invoke form, trigger) inside **whichever of `AGENTS.md` / `CLAUDE.md` already
exists** in the project root — content outside the block is left alone.
smith never creates either file; if neither exists, an agent has nothing to
read until one does — `smith doctor --fix` creates the first `*-md` target
that's selected (`AGENTS.md` by default; `CLAUDE.md` only if `agents.targets`
excludes `agents-md`; nothing if it excludes both) — or just add one by hand.
Re-running `smith install` is idempotent — an up-to-date block produces no
diff, so it's safe to run in CI without dirtying a git-tracked file.

Which targets `smith install` writes to is configurable in
`$SMITH_HOME/config.yaml`:

```yaml
agents:
  targets: [claude, agents-md]   # or claude-md; [] disables emission entirely
```

Leaving `agents.targets` unset auto-detects: `smith install` emits to
whichever of the three targets apply (`claude` — the machine-global per-tool
skill export — plus `agents-md`/`claude-md` for whichever files already
exist). Setting `targets` to an explicit list — including `[]` — overrides
auto-detection entirely; an unknown name is a hard config error, while a
target that merely fails to write only warns — `smith install` still
succeeds for the rest.

The older `skills.export: never` still works and now opts out of **all**
emission, not just the skills dir — it predates agent targets, when that dir
was the only advertisement path, so it reads as "don't advertise my tools".
Use `agents.targets` when you want the finer split (skip the machine-global
skills dir, keep the project-scoped blocks); it wins over `skills.export`.

Note that `config.yaml` is **per-machine**, so `targets: []` opts *you* out,
not your repo — it can't disable emission on behalf of CI or your
contributors. The project-scoped control is the files themselves: the
`*-md` targets only fire when `AGENTS.md`/`CLAUDE.md` already exists, so a
project that shouldn't carry a managed block simply shouldn't have one.

`smith use` runs the tool's self-test sandboxed and writes a reviewable diff;
it never grants trust on its own — the tool becomes PATH-available only once
the adoption is committed/merged and `smith install` runs.

## Runtimes

`smith use` adopts all four runtimes, always vendoring reviewable **source**
(committed), never built artifacts:

- **bash / python** — the script is the entrypoint; symlinked onto PATH.
- **go** — `main.go` is vendored; `smith install` compiles it locally
  (per-platform, git-ignored).
- **python-uv** — `<name>.py` + its hash-locked `<name>.py.lock` are vendored
  (the dep tree, with hashes, is in the PR); `smith install` warms a
  git-ignored tool-local cache from the lock and writes an offline launcher.

For every runtime the PR diff is reviewable source, portable across
teammates' platforms; build/warm happens locally at install.

## Third-party CLIs (via mise)

To standardize an existing third-party CLI — not a smith tool — across a project:

```sh
smith use --mise ubi:DataDog/pup     # also node@20, go:github.com/x/y, aqua:owner/repo
```

This pins the tool + version in the project's committed `mise.toml` and records
it in `.smith/tools.yaml` (`smith list` shows it as `external (mise)`); the
review surface is the `mise.toml` diff. There is **no source review** — you trust
the upstream CLI and mise's fetch, exactly as with mise directly. smith adds a
per-project reviewable pin, a unified `smith list`, and the org allowlist (which
still applies). Teammates run `smith install` (which runs `mise install`) to get
it. There's no self-test and no SKILL export — it's an external binary, clearly
distinct from a source-reviewed smith tool.

## Sandbox host requirements

Tools self-test/run sandboxed, so a functional sandbox is required: macOS
Seatbelt (`sandbox-exec`, built in) or Linux bubblewrap (`bwrap`) with
**unprivileged user + network namespaces enabled**. smith fails closed
otherwise — e.g. GitHub Actions' Ubuntu runners forbid the netns setup
`--unshare-net` needs, so sandboxed runs can't happen there.

A tool declares any extra capabilities it needs in its manifest:

```yaml
sandbox:
  network: true                 # allow network egress
  write: ["~/.cache/mytool"]    # extra writable paths beyond CWD+TMP
  build: true                   # python-uv only: allow dependency source builds
                                # at adopt time (off by default — wheels only)
```

These are **surfaced** when you adopt (`⚠ requests capabilities: …`) so a
reviewer sees them, and **enforced** during the self-test — the tool gets
exactly what it declared, nothing more. Request the minimum; a broad grant is a
review flag.

## Layout

Per **project**:

```
.smith/tools.yaml          adopted tools: source, version, content hash, runtime  (committed)
.smith/tools/<name>/        vendored tool source — reviewed in the PR             (committed)
.smith/bin/                 symlink farm / built binaries, put on PATH           (git-ignored)
.smith/cache/               warmed python-uv caches                              (git-ignored)
mise.local.toml            activation: puts .smith/bin on PATH (machine-specific) (git-ignored)
```

`SMITH_HOME` (default `~/.toolsmith`) is small now — just generated sandbox
profiles and `config.yaml` (review + skills + agent target settings). The code repo (this
directory) is separate.

## Not in scope (v1)

No public contribution hub, no multi-user governance/RBAC, no GUI, no
auto-adopt. The prompt-injection → malware risk means public discovery is
open but *adoption stays a reviewed decision*. See `ROADMAP.md`.

## Org allowlist (optional)

A company can restrict which repos may be adopted — even with a PR — via an
allowlist in `$SMITH_HOME/config.yaml` (provisioned per machine, so a project
PR can't change it):

```yaml
allowlist:
  repos: ["github.com/acme/*", "github.com/acme-tools/lint"]
  # file: /etc/smith/allowlist.txt   # or a managed file, one pattern per line
```

`smith use` refuses (before cloning) any source that matches no pattern;
`smith allowlist` shows the effective policy. Absent = adopt anything. This
is a policy layer on top of the per-project review, for orgs that want central
control.

**Signed allowlist (tamper-evident).** To stop a machine's config from silently
pointing at a widened list, sign the allowlist file with an ed25519 key and pin
the public key:

```sh
smith allowlist keygen                       # → private key file + a public_key to paste
smith allowlist sign allow.txt --key <priv>  # → allow.txt.sig
```
```yaml
allowlist:
  file: /etc/smith/allow.txt
  public_key: <base64 ed25519 public key>
```

To block **rollback** (an attacker serving an old, validly-signed, wider list),
add a version line to the file and bump it whenever you change it — smith records
the highest version it has accepted and refuses an older one:

```
# smith-allowlist-version: 3
github.com/acme/*
```

When `public_key` is set, smith verifies `allow.txt.sig` on every adoption and
**fails closed** (blocks all adoptions) if it's missing, invalid, or the file
was edited. `smith allowlist verify` reports the status. Distribute the public
key + signed file with your fleet config; keep the private key off developer
machines.

## Updating an adopted tool

```sh
smith diff <tool>           # preview: what would change vs the newest version
smith upgrade <tool>        # re-pin one tool to the newest tag (self-tested)
smith upgrade               # ...or every adopted tool → its newest tag
smith upgrade <tool>@<ver>  # pin an exact version
```

`smith upgrade` discovers the newest semver tag of each tool's source repo,
re-runs the sandboxed self-test, and re-pins in `.smith/tools.yaml` — a
reviewable diff like the original adoption. It stops at re-pinning (run `smith
install` after) so new source is reviewed before it lands on PATH; a failed
self-test leaves the old pin untouched. `smith diff` previews the vendored-source
changes first (`--stat` for a summary, `--json` for a machine-readable list).
(Re-running `smith use <repo>@<newver>` by hand still works and is equivalent.)

## Health checks (smith doctor)

Diagnose project + machine health:

```sh
smith doctor            # report only (safe, CI-friendly; exits non-zero on errors)
smith doctor --fix      # apply safe, reversible repairs
smith doctor --json     # machine-readable
```

Checks: mise present, sandbox functional, retired v1 files (fixable); and, in a
project, activation, `.gitignore` coverage, a git-tracked `mise.local.toml`,
vendored-source drift, pinned-but-not-installed tools, and un-sharpened tool
SKILL triggers. `--fix` repairs activation, `.gitignore`, install, and v1 cruft;
it never runs git and never re-fetches over the network.

`smith migrate` does the machine-level v1→v2 cleanup on its own — it backs up
retired `~/.toolsmith` files and strips dead `config.yaml` keys (safe to re-run).
The installer runs it automatically, and `smith doctor --fix` covers the same
cleanup, so you rarely call it directly.
